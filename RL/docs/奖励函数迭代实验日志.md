## 第一轮：v2 基线诊断 —— 发现了什么

### 表象
TensorBoard 曲线看起来很好：
- `rollout/ep_rew_mean`：-273 → **+2628**（涨 10 倍）
- `rollout/ep_len_mean`：183 → **702**（接近 800 上限）
- `train/explained_variance`：0 → **0.896**（Critic 拟合优秀）
- `train/approx_kl`：均值 0.0061（更新稳定）

### 真相（用 eval.py 严格评估）

| 难度 | 成功率 | 首要失败模式 |
|---|---|---|
| d=0.3 | **3%** (3/100) | `crash_not_upright` 42% |
| d=0.5 | **1%** (1/100) | `crash_not_upright` 40% |
| d=0.7 | **0%** | `crash_not_upright` 48% |
| d=1.0 | **0%** | `crash_not_upright` 61% |

### 根因：奖励账本算出来是"躺平划算"

| 状态 | 每步总奖励 |
|---|---|
| 完美正立悬停 | +4.5 |
| 倒扣躺着不动 | **-2.8** |
| 倒扣但努力翻转 | **-5.1** ❌ 比躺平还差 |

**策略的理性选择就是躺平。** 这就是它 42~61% 回合"根本不翻正"的原因。

### 关键教训
> **成功率、奖励、回合长度三者背离时，一定是奖励函数在奖励错误的行为。**
> 尤其"回合长度涨到接近上限"这个信号极具欺骗性 —— 它看起来像"策略学会了存活"，实际是"策略学会了拖延"。

## 第二轮：v3 改动 —— 成功

### 改动（三处，一次只改这一组）

```python
# 1) 姿态项：从"正立有奖"改为"倒扣有罚"
r_up = -3.0 * (1.0 - up_z)          # 原: 3.0 * up_z

# 2) 角速度项：按姿态分档，全部为负
if up_z < 0.3:   k_rate = 0.003     # 躺着：罚轻，允许暴力翻转
elif up_z < 0.8: k_rate = 0.01      # 中途：原力度
else:            k_rate = 0.03      # 立起：罚 3 倍，逼它稳住
r_rate = -k_rate * omega_norm ** 2

# 3) 垂直速度项：从"按时间"改为"按姿态"
if up_z < 0.7: r_vz = 0.0           # 原: if k < 0.5*ctrl_hz
else:          r_vz = -0.3 * abs(vz + descend_rate)
```

### 改后账本（关键改善）

| 状态 | v2 | v3 | 变化 |
|---|---|---|---|
| 倒扣躺着 | -2.8 | **-5.50** | 躺平代价翻倍 |
| 倒扣翻转中 | -5.1 | **-4.31** | 翻转比躺平好 |
| 翻转中途 (up_z=0.5) | ≈-3.9 | **-1.65** | ✅ 上坡路出现 |

### 结果

| 难度 | v2 | v3 | 提升 | 显著性 |
|---|---|---|---|---|
| d=0.3 | 3% | **53%** | +50pp | ✅ CI 不重叠 |
| d=0.5 | 1% | **41%** | +40pp | ✅ 显著 |
| d=0.7 | 0% | **33%** | +33pp | ✅ 显著 |
| d=1.0 | 0% | **24%** | +24pp | ✅ 显著 |

**失败模式变化（d=0.3）**：
- `crash_not_upright`：42 → **5**（✅ 姿态问题基本解决）
- `out_of_bounds`：39 → 28（仍高，成为新瓶颈）

### 一个反常但正确的现象
v3 的 `ep_rew_mean`（624）比 v2（2628）**低得多**，但真实成功率高一倍。

> **教训：奖励函数被改动后，跨实验的 reward 绝对值不可比。** 必须用任务级指标（成功率）判断好坏。

## 第三轮：v4 改动 —— 失败的负结果

### 假设
v3 的 `out_of_bounds` 占 28~41%，说明策略不在乎水平漂移。把 `r_vxy` 从 0.2 提到 0.6 就能收住。

### 改动
```python
r_vxy = -0.6 * math.sqrt(vx*vx + vy*vy)    # 原: -0.2 * ...
```

### 结果：反而更差

| 难度 | v3 | v4 | 差值 |
|---|---|---|---|
| d=0.3 | 53% | 45% | -8pp |
| d=0.5 | 41% | 32% | -9pp |
| d=0.7 | 33% | 25% | -8pp |
| d=1.0 | 24% | 22% | -2pp |

### 为什么失败：`out_of_bounds` 没降，但 `timeout_unstable` 暴涨

| 难度 | `out_of_bounds` v3→v4 | `timeout_unstable` v3→v4 |
|---|---|---|
| d=0.3 | 28 → 25（几乎没动） | 13 → **21** |
| d=0.5 | 41 → 38（几乎没动） | 6 → **19** |
| d=0.7 | 37 → 37（完全没动） | 8 → **17** |
| d=1.0 | 34 → 26 | 1 → 6 |

### 根因
`r_vxy` 是**全局惩罚**。倒扣翻滚时物理上必然伴随水平速度 —— 加大全局惩罚等于**给"翻转"这条路加税**。策略被迫在"冒险翻转"和"保守不动"之间再次倒向后者，于是「立起来但不敢动、不收敛」。

### 关键教训
> **惩罚项必须问清楚"什么时候该生效"**。
> `r_vz` 已经用了"按姿态触发"的思路（`up_z>0.7` 才罚），而 `r_vxy` 却做成了全局的 —— 这是设计不一致。
> 全局惩罚会误伤必要的中间过程状态。

## 方法论沉淀

### 1. 三级评估流水线（缺一不可）

| 层级 | 工具 | 回答的问题 |
|---|---|---|
| L1 训练监控 | TensorBoard / `compare_tb.py` | 策略**在学吗**？ |
| L2 批量量化 | `eval.py` | 真实能力**多少**？怎么死的？ |
| L3 定性回放 | `play.py` | 失败**长什么样**？ |
| L4 消融对比 | `report.py` | 改动**到底有效吗**？ |

### 2. 实验纪律

- **固定种子集**：所有对比都用同一批初始条件，否则无法归因
- **一次只改一个变量**：v4 失败就因为改了系数却没想清楚作用范围
- **看置信区间不看裸百分比**：45% vs 53% 在 100 样本下 CI 重叠，不能断言退化
- **负结果必须记录**：v4 的失败直接催生了 v5 的正确设计

### 3. 奖励设计的检查清单

设计任何一个奖励项时，问三个问题：
1. **它在什么时候生效？**（全局 vs 按状态触发）
2. **它会不会误伤必要的中间过程？**（如翻转时的角速度、水平速度）
3. **目标状态和"放弃状态"的收益差够不够大？**（算一遍账本）

## 第五轮：E-A 有效旋转奖励 —— 惨重失败（v6）

### 动机
v5（MLP, 200万步）达到 54%/52%/40%/26% 后不再提升，判定为架构/信息量瓶颈。
高飞团队报告的 P2 建议：不要急于上 GRU/LSTM，可先用 History Stacking 增强输入。
但在那之前，先试一个更便宜的改动：给「有效旋转」正奖励，逼策略果断翻转。

### 设计（思路本身是对的）
不直接奖励 |ω|（会被刷分），而是奖励「真正让姿态变好的那部分旋转」：

```python
delta_up_z = up_z - prev_up_z
if up_z < 0.7 and delta_up_z > 0:
    r_effective_rot = 0.8 * min(delta_up_z / dt, 8.0)   # ← 系数错了
```

理据：绕 z 轴（yaw）转不改变倾角 → delta_up_z≈0 → 拿不到分；
绕 xy 轴但方向错 → delta_up_z<0 → 拿不到分。
有效性判断已内含其中，不需要按轴区分奖励大小。

### 结果：灾难性退化

| 难度 | v5(2M) | v6(E-A) | 变化 | 首要失败模式 |
|---|---|---|---|---|
| d=0.3 | 54.0% | **2.3%** | -51.7pp | `crash_upright` 69% |
| d=0.5 | 51.6% | **2.6%** | -49.0pp | `crash_upright` 67% |
| d=0.7 | 40.1% | **1.2%** | -38.9pp | `crash_upright` 67% |
| d=1.0 | 25.6% | **1.0%** | -24.6pp | `crash_upright` 51% |

**同时翻转确实变快了**：recover_time 从 0.465s → 0.36s。
即：策略学会了「翻得更快」，但完全放弃了高度控制。

### 根因：奖励量级失衡（又是一个没先算账本的错误）

| 奖励项 | 数值范围 | 对比 |
|---|---|---|
| `r_up`（姿态） | -6.0 ~ 0 | 基准 |
| **`r_effective_rot`** | **0 ~ +6.4** | **与 r_up 同级** |
| `r_vz`（高度） | 0 ~ -1.5（典型） | 被压到不起眼 |

单步 up_z 只要改善 0.05 就能拿 +6.4 分 —— 足以抵消「完全躺平」的全部代价。
策略的理性选择变成：「只要翻得快，高度掉光也无所谓」。

### 教训（与 v4 同一类错误）
> **加任何一个奖励项，必须先算清它与现有项的相对量级。**
> 辅助奖励的定位是「引导方向」，其单项上限不应该超过主奖励项的 10~20%。
> 一旦辅助奖励能和主奖励抗衡，策略就会用它来「赎买」违反主奖励的行为。

### 修正：E-A2
| 参数 | E-A（失败） | E-A2（修正） |
|---|---|---|
| 系数 | 0.8 | **0.08**（1/10） |
| 单项上限 | 8.0 | **3.0** |
| 实际单步最大 | +6.4 | **+0.24**（仅占 r_up 满罚的 4%） |


### E-A2 修正后：成功

| 难度 | v5(2M) | E-A2 | 变化 | 显著性 |
|---|---|---|---|---|
| d=0.3 | 54.0% [51,57] | **61.1%** [58,64] | +7.1pp | ✅ **CI 不重叠** |
| d=0.5 | 51.6% [48,55] | **56.5%** [53,60] | +4.9pp | ⚠️ 重叠 |
| d=0.7 | 40.1% [37,43] | **44.2%** [41,47] | +4.1pp | ⚠️ 重叠 |
| d=1.0 | 25.6% [23,28] | **27.7%** [25,31] | +2.1pp | ⚠️ 重叠 |

**回正耗时（全部加快，越难提升越多）**：
| 难度 | v5 | E-A2 | 提升 |
|---|---|---|---|
| d=0.3 | 0.465s | 0.41s | -12% |
| d=0.5 | 0.675s | 0.61s | -10% |
| d=0.7 | 0.98s | 0.812s | -17% |
| d=1.0 | 1.2s | 0.938s | **-22%** |

### 量级敏感性（同一设计的两个极端）

| 版本 | 系数 | 单步上限 | d=0.3 | 翻转耗时 | 结果 |
|---|---|---|---|---|---|
| E-A | 0.8 | +6.4 | 2.3% | 0.36s | ❌ 崩盘 |
| E-A2 | 0.08 | +0.24 | 61.1% | 0.41s | ✅ 成功 |

**系数差 10 倍，结果从崩溃变成功。** 这说明奖励量级必须精确校准，
且「翻转速度」不是越快越好 —— 0.36s 虽然更快但代价是高度崩盘。

### 当前最优版本：v6b (E-A2)

配置：v5 全部奖励项 + `r_effective_rot = 0.08 * min(Δup_z/dt, 3.0)`。

## 附加分析：按初始高度分组评估

### 动机
怀疑「初始高度过低导致物理上不可能成功」拉低了总体成功率。
（环境初始高度范围实际为 1.5~2.5m，此前口误说成 2.0~3.0m 已更正。）

### 结果（v6b E-A2，1000 回合/档，固定种子集）

| 高度区间 | 样本 | d=0.3 | d=0.7 | d=1.0 |
|---|---|---|---|---|
| 1.5-1.8m | 302 | 62.6% | 41.7% | **22.8%** |
| 1.8-2.1m | 300 | 63.3% | 44.0% | **29.0%** |
| 2.1-2.4m | 284 | 56.0% | 44.7% | **28.9%** |
| 2.4-2.6m | 114 | 64.0% | 50.0% | **34.2%** |
| 合计 | 1000 | 61.1% | 44.2% | 27.7% |

### d=1.0 的失败构成（关键）

| 高度区间 | `crash_not_upright`（翻不过来） | `crash_upright`（刹不住） |
|---|---|---|
| 1.5-1.8m | 55.6% | 9.6% |
| 1.8-2.1m | 51.3% | 8.3% |
| 2.1-2.4m | 48.2% | 7.7% |
| 2.4-2.6m | 46.5% | 3.5% |

### 结论
1. **高度影响存在但有限**：d=1.0 从 22.8%→34.2%（+11.4pp），d=0.3 基本无差别。
2. **真正的瓶颈不是高度**：即使在 2.4m 以上，仍有 46.5% 的回合「根本翻不过来」。
3. **`crash_upright`（刹不住）占比很小（3.5~9.6%）**，且高度越高占比越低。
   → 说明「翻正后高度控制」不是主要问题，「翻转能力不足」才是。
4. **下一步应该聚焦「180° 纯倒扣下的姿态恢复」**，而不是继续优化高度控制或物理参数。

## 第六轮：E-A3 系数加倍 —— 再次崩盘（v7）

### 动机
E-A2 (系数 0.08) 取得 61.1% 最优。尝试「一点点提高奖励量级」看能否继续提升。

### 变更
`r_effective_rot = 0.08 → 0.16`（仅 2 倍），其余完全不变。

### 结果：再次崩盘（与 E-A 同一种模式）

| 系数 | 单步上限 | 占 r_up 比例 | d=0.3 | d=1.0 | 首要失败 |
|---|---|---|---|---|---|
| 0（无） | 0 | 0% | 54.0% | 25.6% | — |
| **0.08** | **+0.24** | **4%** | **61.1%** | **27.7%** | timeout_unstable |
| **0.16** | +0.48 | 8% | **2.0%** | **1.0%** | `crash_upright` 48% |
| 0.8 | +6.4 | 107% | 2.3% | 1.0% | `crash_upright` 69% |

**注意 0.16 和 0.8 的失败模式完全相同**（都是 `crash_upright` 主导）——
说明它们已进入同一个「崩溃区」，2 倍和 10 倍的差别在这个区里无意义。

### 关键发现：这是相变，不是渐变

奖励劫持（reward hacking）表现为**相变（phase transition）**：
- 临界点以下：辅助奖励只引导方向，策略行为正常
- 临界点以上：策略整体切换到「刷分模式」，性能断崖下跌

机制：当 `r_effective_rot` 能抵消掉大部分 `r_vz`（高度惩罚）时，
「放弃高度快速翻转」比「控高度慢慢翻」更划算。一旦策略发现这条捷径，
正反馈会推动它全面倒向该模式。

### 结论
1. **「一点点提高奖励量级」在这个奖励项上不可行** —— 0.08 到 0.16 就是最优到全崩。
2. **辅助奖励的安全上限约为主惩罚项的 5%**（0.24/6.0 = 4% 安全，0.48/6.0 = 8% 崩盘）。
3. **当前最优配置锁定为系数 0.08**，已恢复到代码中。
4. 想继续提升 d=1.0 的 `crash_not_upright`（46~56%），必须换别的思路，
   不能再在这一个奖励项上加码。

## 第七轮：History Stacking —— 失败（v8）

### 动机
参考高飞团队报告 P2 建议：不急于上 GRU/LSTM，用「历史帧堆叠」让无记忆 MLP 也能看到时间趋势。

### 实现
观测 22 维 → 43 维（额外堆叠最近 3 帧的 `[ang_vel(3), last_action(4)]`）。
`--history 3` 参数化，`reset` 时清空历史缓冲避免跨 episode 串味。

### 结果：严重退化

| 难度 | E-A2 (22维) | v8 (43维) | 变化 | 首要失败模式 |
|---|---|---|---|---|
| d=0.3 | 61.1% | **7.8%** | -53pp | `out_of_bounds` **60%** |
| d=0.5 | 56.5% | **6.9%** | -50pp | `out_of_bounds` 61% |
| d=0.7 | 44.2% | **6.1%** | -38pp | `out_of_bounds` 54% |
| d=1.0 | 27.7% | **2.9%** | -25pp | `crash_not_upright` 51% |

**失败模式剧变**：E-A2 的 `out_of_bounds` 仅 5~8%，v8 暴涨到 54~61%。
即策略完全放弃了水平位置控制。

### 根因（三重错误）

1. **尺度不一致**：历史里的 `ang_vel` 又除以了 10 归一化，
   而原 22 维观测中的 gyro 已经是除以 10 的。特征尺度不统一。
2. **堆叠 action 导致行为惯性**：把 `last_action` 堆 3 帧，
   相当于告诉网络「我过去 3 帧做了什么」，策略倾向于重复历史动作而非根据当前状态纠正。
3. **网络容量没变**：观测 22→43 维（首层参数 1408→2752），
   但网络仍是 64x64。新增的 21 维信息会挤占原本用于姿态判断的容量。

### 重要发现：训练内评估与正式评估的判据差异

| 评估方式 | 判据 | v8 在 d=1.0 |
|---|---|---|
| `train_ppo.evaluate_policy` | 宽松（曾翻正 + 未坠地） | 28.0% |
| `eval.py` 标准 | 严格（活满全程 + 状态收敛） | **2.9%** |

**差 7 倍**。这是预期的判据差异，不是 bug。
教训：**训练时的 `eval/success_rate` 只能看趋势，不能当结论。
所有跨实验对比必须用 `eval.py` 的严格判据。**

### 结论
History Stacking 这条路在当前实现下失败。若要重试，至少需要：
- 统一特征尺度（历史里的 ang_vel 不再除以 10）
- 不堆叠 action，只堆叠 ang_vel + 姿态历史
- 相应加大网络宽度（如 64→128），给新增信息留出容量

## 第八轮：Tanh 输出压缩 —— 失败（v10）

### 动机
逐层激活值追踪发现：E-A2 模型的动作输出范围是 [-9.73, +8.41]，
1000 个状态采样中仅 30.9% 落在 [-1,1] 内，**69.1% 被 env 的 np.clip 截断**。
根因：action_net 是最后一层且无激活，其权重 sum|W| ≈ 9，理论上限就是 ±9。
假设：给输出加 Tanh 压缩，让策略学会连续调节而非二值开关。

### 实现
自定义 `TanhActorCriticPolicy`，在 `action_net` 后追加 `nn.Tanh()`。
参数量不变（Tanh 无参数），输出严格 ∈ (-1,1)。

### 结果：灾难性退化

| 难度 | E-A2 (无Tanh) | v10 (有Tanh) | 变化 | 首要失败 |
|---|---|---|---|---|
| d=0.3 | 61.1% | **0.2%** | -60.9pp | `crash_upright` 50% |
| d=0.5 | 56.5% | **0.6%** | -55.9pp | `crash_upright` 52% |
| d=0.7 | 44.2% | **0.6%** | -43.6pp | `crash_upright` 55% |
| d=1.0 | 27.7% | **0.6%** | -27.1pp | `crash_upright` 45% |

### 根因：Tanh 的梯度消失

| 版本 | 输出范围 | 饱和比例 (|a|>0.9) | 成功率 |
|---|---|---|---|
| E-A2 无Tanh | [-5.05, 8.23] | 58.1% | 61.1% |
| v10 有Tanh | [-1.00, 1.00] | **54.6%** | 0.2% |

**关键发现**：加 Tanh 后饱和比例几乎没变（54.6% vs 58.1%）。
说明「饱和」不是输出层缺少压缩导致的，而是**策略本身就想输出极端值**。

而 Tanh 在饱和区梯度极小：
- |a|=0.99 → 梯度 0.02
- |a|=0.999 → 梯度 0.002
- 策略 54.6% 时间处于 |a|>0.9 → 一半以上时间梯度趋近 0
→ PPO 无法有效更新这部分参数 → 训练停滞

### 教训
> **「加激活函数限制输出范围」这个直觉在 RL 里是反的。**
> 监督学习里加 Tanh 是为了限制输出范围，防止过拟合；
> RL 里策略处于饱和区时梯度消失，会直接摧毁学习能力。
> 无 Tanh 版本虽然输出 ±8，但梯度正常，clip 只是「事后补救」，
> 反而保住了学习能力。

### 结论
1. **Tanh 输出压缩方案失败，不建议采用。**
2. 真正的问题不是「输出超界」，而是「策略倾向于输出极端值」。
   要解决它，应该从**奖励设计**（让精细控制有收益）入手，
   而不是从**网络结构**（硬限制输出）入手。
3. 当前最优仍是 E-A2：61.1% / 56.5% / 44.2% / 27.7%。

## 第九轮：网络加宽 [64,64]→[128,128] —— 失败（v11）

### 动机
v10（Tanh）失败后，重新审视：既然「输出饱和」不是缺陷（倒扣时猛转是对的），
那瓶颈是否在「网络容量不足」？

### 实现
`--width 128`，`net_arch=[128,128]`，不加 Tanh。
参数量 11,593 → 39,561（3.4 倍）。

### 结果：全面退化

| 难度 | E-A2 (64宽) | v11 (128宽) | 变化 | 显著性 |
|---|---|---|---|---|
| d=0.3 | 61.1% | **54.3%** | -6.8pp | ✅ CI 不重叠（显著退化） |
| d=0.5 | 56.5% | **47.7%** | -8.8pp | ✅ 显著退化 |
| d=0.7 | 44.2% | **38.8%** | -5.4pp | ✅ 显著退化 |
| d=1.0 | 27.7% | **24.1%** | -3.6pp | ⚠️ CI 重叠 |

### 根因
网络过参数化（over-parameterization）：
- 观测只有 22 维，任务并不复杂
- 参数越多，PPO 的策略梯度估计方差越大，探索空间越大，越难收敛
- 相同步数下，大网络的样本效率反而更低

### 网络结构探索的完整结论

| 实验 | 改动 | 结果 | 判定 |
|---|---|---|---|
| v8 | History Stacking（43维） | 7.8% | ❌ 崩盘 |
| v10 | Tanh 输出压缩 | 0.2% | ❌ 崩盘 |
| v11 | [128,128] 加宽 | 54.3% | ❌ 显著退化 |

**结论：网络结构层面已经没有优化空间了。**
- 加信息（History）→ 失败
- 加约束（Tanh）→ 失败
- 加容量（128宽）→ 失败

**当前最优仍是 E-A2（[64,64]，无 Tanh，22维观测）：61.1% / 56.5% / 44.2% / 27.7%**

### 下一步方向（mj 提出）
分阶段训练（两阶段）—— 详见 `docs/分阶段训练设计方案.md`。
核心洞察：倒扣时猛转本来就是对的，精细调节应该只在回正后做。
一个网络无法同时胜任两种控制风格，这才是真正的瓶颈。

## 第十轮：分阶段训练 Phase 1（翻转策略）—— 重大成功

### 动机
九轮实验证明网络结构无优化空间（v8/v10/v11 全败），瓶颈在**任务定义**。
mj 提出的关键洞察：

> **倒扣时激进猛转本来就是对的，精细调整应该在基本回正之后才做。**

一个网络无法同时胜任「倒扣暴力翻转」与「翻正后精细悬停」两种矛盾的控制风格。
因此拆成两个阶段，各训一个专用策略。

### Phase 1 设计

| 项 | 定义 |
|---|---|
| 触发区间 | `up_z < 0.5`（tilt > 60°） |
| 初始采样 | `tilt ∈ [72°, 180°]`（`up_z ∈ [-1, 0.31]`），角速度 2~12 rad/s |
| 奖励 | **只保留** `r_up` + `r_effective_rot` + `r_bonus` + 存活常数 |
| 不罚 | 高度、水平速度、角速度（这些都是翻转的合理代价） |
| 终止 | `up_z > 0.7` 视为交接成功，+20 奖励并结束 |

### 实现过程中修复的关键 bug
`evaluate_policy` 原本用端到端判据（要求活满 800 步且最终状态达标）。
但 Phase 1 是「达标即终止」的设计，永远活不满全程 → 评估永远是 0%。
**修复**：给 `evaluate_policy` 加 `phase` 参数，Phase 1 用「是否曾达 up_z>0.7」判据。

验证：同样的 PD 控制器在 Phase 1 判据下从 0% 变 100%，证明判据修对了。

### 结果：100% 成功

| 指标 | 端到端 E-A2 | Phase 1 专用 | 提升 |
|---|---|---|---|
| 倒扣翻正成功率 | 27.7% | **100.0%** | **+72.3pp** |
| 翻正耗时 | 0.94s | **0.10~0.14s** | **快约 7 倍** |

**行为抽样**（5 回合，全部在 21~27 步内完成交接）：
```
回合1: max_up_z=0.72, 步数=24
回合2: max_up_z=0.81, 步数=21
回合3: max_up_z=0.74, 步数=24
回合4: max_up_z=0.78, 步数=27
回合5: max_up_z=0.74, 步数=21
```

### 关键洞察
1. **任务分解的效果远大于奖励微调**：端到端调了 6 轮奖励才从 0% 到 27.7%，
   而 Phase 1 单一任务一次就 100%。
2. **速度快 7 倍是意外收获**：因为 Phase 1 不用分心管高度和速度，可以全力翻转。
3. **这印证了 mj 的判断**：一个网络同时干两件矛盾的事，才是真正的瓶颈。

### 结论
Phase 1 达成设计目标。下一步训练 Phase 2（稳定策略），
然后用 `eval_hierarchical.py` 做联合评估，与 E-A2 端到端对照。

## 第十一轮：分层联合评估 v12 —— 单阶段都好，串联就崩

### 结果（端到端环境 + 滞回切换 + 严格判据，50 回合粗筛）

| 难度 | E-A2 端到端 | P1+P2 联合 | 判定 |
|---|---|---|---|
| d=0.3 | 61.1% | 46% | ❌ 退化 |
| d=1.0 | 27.7% | **8%** | ❌ 严重退化 |

单看每个 Phase 都及格（P1 翻转 100%、P2 稳定 94%），串联后反而不如端到端。

### 诊断数据（eval_hierarchical.py 的交接统计立了大功）

| 诊断项 | d=0.3 | d=1.0 |
|---|---|---|
| 交接时角速度中位 | 9.7 rad/s | **82.6 rad/s** |
| 交接时角速度 max | 21 rad/s | 178 rad/s |
| P2 训练时见过的角速度 | — | 仅 0.5~4 rad/s |

### 根因：终止条件塑造了 P1 的盲区
P1 在 Phase 1 环境学到的是「全力量猛翻到 0.7，环境就结束」——
它从未需要学「翻正后刹车」，因为训练环境不需要。
联合环境里，P1 以 82 rad/s 的旋转惯性"甩"给 P2，
P2 从未见过这种状态，直接失控。

这正是设计文档预警的「分布偏移」风险，实际严重度远超预期。

### v13 修复方案（进行中）
1. **P1 交接条件收紧**：`up_z>0.7 且 |ω|<4` 才算交接成功
   → 迫使 P1 学会完整动作：翻过来 + 停得住
2. **P1 交接奖励分级**：刹得越干净奖励越高（ω=0 给 +20，ω=4 给 +8）
   → 防止刷分：必须真的刹住才能拿高分
3. **P2 初始采样放宽**：角速度范围 0.5~4 → 0.5~6 rad/s
   → 覆盖 P1 可能的交接状态，留安全裕量


### v13 的第一次失败与 v13b 修正（重要教训）

v13 初版（要求 ω<4 才给满交接奖，否则 +2 也终止）训练 25 万步成功率 0%。
复盘发现三个设计错误：

1. **逃逸出口**：「没刹住也终止(+2)」让策略可以廉价地翻正一次、领小奖、重开。
2. **躺平陷阱回归**：翻转全程要付 -3(1-up_z) 的持续罚（25 步 ≈ -75），
   而刹车没有独立的梯度信号——「早死早超生」比冒险学刹车便宜。
3. **无刹车梯度**：翻转中途（up_z<0.7）完全不罚角速度，
   策略在冲过 0.7 之前没有任何理由开始收力。

v13b 三处修正：
- a) 接近区（up_z∈[0.3,0.7)）减速惩罚线性爬坡 → 提供"快到边界先收力"的梯度
- b) 越界未刹（up_z≥0.7 且 ω≥4）每步 -0.01·min(ω,40)² 重罚
- c) 取消 +2 逃逸出口：唯一出路是刹住后干净交接（+20-3ω）或坠地

账本验证：刹车路径 -58 vs 猛冲路径 -83 且持续流血 vs 躺平 -4400，梯度方向正确。

### 教训（RL 奖励设计的元规则）
> **终止条件本身就是奖励结构的一部分。**
> 任何「达标即终止」的设计，都要问：达标瞬间的【状态导数】（角速度、速度）
> 是否也被约束了？否则策略一定学会「冲过终点线」而不是「停在终点线」。
> 这个 bug 在端到端训练里被 r_up 的连续梯度掩盖了，只在分层拆分后暴露。


## 第十二轮：v14 —— P2 补位置能力 + 判据可达性教训

### v13 联合评估的两个真凶（诊断实锤）
1. **P2 完全没有位置保持能力**：奖励里没有水平位置项，
   单独跑出界回合末位置中位 5.0m、水平速度 2 m/s → d=0.3 的 40% out_of_bounds。
2. **切换条件与 P1 刹车能力脱节**：up_z>0.7 瞬间切换时 ω 中位 8.1~14.9 rad/s，
   超出 P2 经验范围（≤6）→ 交接不平滑。

### v14 修复
1. P2 奖励加 `r_pos = -0.1 × 水平距离`；初始 xy 采样放宽 [-0.3,0.3]→[-1,1]
   （不加位置项 P2 学不会回中；不放宽采样 P2 没见过偏离状态，回中项无从学起）
2. 稳定判据加水平速度条件（防"斜着冲过判定点"）
3. 联合评估切换条件改为 `up_z>0.7 且 ω≤6`（对齐 P2 训练分布）
4. P1 不重训（v13b 已含刹车能力）

### ⚠️ 重要教训：判据可达性检查
第一版 v14 把水平速度阈值定为 0.5，训练 25 万步全程 0%。
用 PD 一测：**PD 在 0.5 阈值下只有 2/10 达标** —— 判据近乎不可达，
RL 当然全程 0%。放宽到 1.0（PD 6/10 可达）后重启。

> **元规则：给任务加新判据/新约束时，先用 PD 基线测一遍可达性。**
> 连手工调好的控制器都达不到的判据，RL 在有限步数内也几乎不可能达到。
> 这个检查只要 30 秒，能省掉 35 分钟的废训练。


### v14 → v15：判据设计的连环教训（本轮最值钱的一课）

v14（r_pos 位置项 + 判据加 vxy<1.0 + 采样 ±4）训练 100 万步全程 0%。
停止训练后逐项诊断，发现三个叠加错误：

**错误 1：惩罚模型看不见的量（最严重）**
v14 加了 `r_pos = -0.1×水平距离`，但检查观测构造发现：
22 维观测里【根本没有 x,y 位置】（只有高度 z）！
模型看不见原点，罚位置 = 给奖励注入不可解释的噪声，
反而干扰了姿态学习（诊断：末态 up_z 只有 0.7~0.8，v13 版能稳到 0.98）。

**错误 2：判据可达性检查不够严格**
v14 判据加水平速度条件后，PD 达标率从 9/10 掉到 2~6/10。
"6/10 勉强可达"其实不够 —— RL 需要判据处于"高价值区"才能形成有效梯度，
PD 都吃力的判据，RL 在 100 万步内学不到。v15 回退后 PD 10/10。

**错误 3：采样范围拍脑袋**
±4 m/s 的"安全裕量"没有数据支撑。实测 P1 v13b 交接时
水平速度 max 只有 2.8 m/s（d=1.0），±3.0 就够覆盖，
多出来的采样预算全浪费在真实中不存在的状态上。

### v15 方案（数据驱动，三处修正）
1. 删 r_pos（不可见量不进奖励）
2. 判据回退 v13 版（PD 10/10 可达）；水平收敛改由 r_vxy_stab 梯度负责，
   系数 0.5→1.0（漂移 2 m/s 罚 -2.0/步，与 r_up 满幅同级）
3. 水平初速采样 ±3.0（实测 P1 交接 max 2.8，恰好覆盖）

### 元规则沉淀（三次踩坑归纳）
> 1. **奖励的每一项必须作用于观测里可见的量。** 加奖励项前先查观测向量。
> 2. **终止判据必须让 PD 基线轻松可达（≥8/10）。** 判据负责"要不要奖励"，
>    奖励梯度负责"怎么做得更好"—— 别把难度压进判据。
> 3. **分布对齐要用实测数据，不要拍脑袋加裕量。** 先测上游阶段的真实
>    交接状态分布，再定下游的采样范围。


## 第十三轮：v15b 联合评估 —— 首次接近端到端，差距收敛到噪声级

### 本轮做对的三件事（零训练成本）
1. **切换阈值对齐**：HANDOFF_OMEGA_MAX 6.0→4.0（精确对齐 P1 训练终止条件）
   → d=0.3 从 46% 升至 58%（粗筛），交接 ω 全部压到 ≤4.0
2. **阈值扫描定最优**：3.0/3.5/4.0 三点实测，4.0 最优 —— 因为 4.0 正是
   P1 环境的交接终止条件，训练与部署的切换逻辑完全一致
3. **避免无效重训**：发现联合评估跑在端到端环境（phase=0），
   P2 的训练配置不影响评估 → 现有 p2_v13 直接可用，省 35 分钟废训练

### 1000 回合正式评估（固定种子集）

| 难度 | E-A2 端到端 | 分层 P1+P2 | 差值 | 显著性 |
|---|---|---|---|---|
| d=0.3 | 61.1% | **63.1%** | **+2pp** | CI 重叠 |
| d=0.5 | 56.5% | 50.9% | -6pp | ⚠️ CI 重叠 |
| d=0.7 | 44.2% | 38.5% | -6pp | ⚠️ CI 重叠 |
| d=1.0 | 27.7% | 24.3% | -3pp | CI 重叠 |

**分阶段方案首次与端到端打平（d=0.3 甚至反超），所有差距收敛到噪声级。**

### 剩余瓶颈的定位（诊断数据）
1. **out_of_bounds 仍是主失败模式（30~56%）**：

## 第十四轮：v16 架构重构 —— 职责按「动作类型」划分（mj 定调）

### 背景：一次架构层面的自我修正
mj 对 v13b 提出关键质疑：
> 「不应该在 P1 阶段加入刹车，否则就跟之前一样，又要负责翻转又要负责刹车。
>   分阶段应该是第一阶段纯翻转，第二阶段从高速到稳定。」

这个批评直接推翻了我 v16 初稿（给 P1 加水平速度惩罚）的方向。

### 认知修正：错误的归因链

| 版本 | 做法 | 结果 | 当时的归因 |
|---|---|---|---|
| v12 | P1 纯翻转，翻正即交 | 联合崩到 8% | ❌ "P1 甩太快"（错误） |
| v13b | 逼 P1 刹车到 ω<4 才交接 | P1 100% 但联合 24.3%，out_of_bounds 56% | 靠补丁绕过，未解决根因 |
| v16 | P1 纯翻转 + P2 覆盖实测交接分布 | 训练中 | ✅ 正解 |

**真正的归因**（v16 用数据确认）：
从 180° 翻到正立，交接瞬间角速度 12~26 rad/s 是**物理必然**（旋转不可能瞬间归零）。
v12 崩盘不是 P1 的错，而是 **P2 训练分布太窄（仅 0.5~4 rad/s）**。
正确解法是「下游适配上游的真实输出」，而不是「上游阉割自己迁就下游」。

### 架构原则（写入项目规范）
> **分阶段的职责必须按「动作类型」划分，不能按「姿态阈值」划分。**
> - P1 = 加速/转向类（施加力矩改变姿态方向）→ 只管姿态
> - P2 = 阻尼/减速类（刹旋转 + 刹平移 + 收姿态）→ 只管速度收敛
>
> 这样每个阶段内部目标单一、无矛盾。
> 反例：给 P1 加刹车 = 让同一个网络同时"加速翻正"和"减速刹车"，必然内耗。

P2 同时管「刹旋转」和「刹平移」不违反这条原则 ——
两者都是同一类动作（阻尼减速），目标方向一致（都往 0 收敛）。

### 实测交接分布（v16 的数据依据）
用 P1 纯翻转跑 100 回合，记录 up_z 首次越过 0.7 时的状态：

|---|---|---|---|---|---|
| d=0.7 | 12.8 | 18.3 | 23.5 | 1.31 | 4.41 |
| d=1.0 | 14.3 | 19.2 | **26.0** | 1.69 | 4.20 |

### P2 判据可达性验证（PD 基线）
| P2 初始 ω 上限 | PD 达标率 | 结论 |
|---|---|---|
| ≤12 | 9/10 | 轻松 |
| ≤20 | 7/10 | 可达 |
| ≤26 | 4/10 | ⚠️ 极限区 |

回退方案：若 P2 学不动，降上限到 20（覆盖 90%）。

### 采样实现的关键修正
原 per-axis `uniform(-m, m)` 采样会让向量模长达到 `m*sqrt(3)≈1.73m`
（实测 ω 目标 26，实际采到 31.9）。改为 **模长均匀 + 随机单位方向**：
```python
def _rand_vec3(rng, mag_min, mag_max):
    mag = rng.uniform(mag_min, mag_max)
    v = rng.normal(size=3); v /= norm(v)
    return v * mag
```
修正后：|ω| max 25.9（目标 26）、|vxy| max 4.4（目标 4.4）、up_z 0.65~0.85，精确对齐。

纯姿态目标的路线验证成功 —— 单一职责确实学得快。

|---|---|---|---|---|---|

**P2 v18**：仍 0%（诊断：角速度达标从 0→16 步 ✅ 混合项生效，但姿态达标从 12→0 步 ❌ 退步）

### 三个关键结论

**结论1：覆盖扩展的效果是「大角度变强、小角度变弱」**
- d=1.0：60% → **70%**（+10pp，覆盖生效）
- d=0.7：78% → 67%（-11pp，采样密度被稀释）
- 翻转速度：38 → **28 步**（快 26%，因为学会了更猛的翻转）
- **代价**：训练环境成功率 97.5% → 63%，因为任务变难但训练步数没变

> **元规则：任务难度提升时，训练预算必须同步提升。**
> ω 覆盖从 18.3 扩到 26（跨度 +42%），200 万步不够学充分。

**结论2：混合项解决了低区梯度塌陷，但暴露了姿态项的量纲问题**
- ω 达标步数：0 → 16（混合项有效 ✅）
- 姿态达标步数：12 → 0（姿态项失效 ❌）
- 账本诊断：`r_up = -3(1-up_z)` 满幅仅 -3，而 `vz=-5` 时 `r_vz=-3.0`
  → 姿态崩到 66°(up_z=0.4) 才罚 -1.8，被下坠项完全压过

**结论3：根本症结是「量纲不对等」**
- 姿态 `up_z` 是 [-1,1] 有界量
- 速度 `vz` 是无界量（可到 -6 m/s）
- 用同一套线性形式（`-k*误差`）描述两者，必然导致速度项主导

### v19 拟案（已算账本验证）

```python
if up_z < 0.85:
    r_up = -12.0 * (0.85 - up_z) / 0.85    # up=0 罚 -12，姿态崩时重罚
else:
    r_up = +2.0 * (up_z - 0.85) / 0.15     # up=1.0 奖 +2，鼓励顶满
```
